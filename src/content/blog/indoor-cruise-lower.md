## 前言

上篇已经使用 LIVOX Mid-360 查看了点云，并用 RTAB-Map 完成了第一次室内建图。

但地图能显示出来，不代表小车已经会巡航。真正把车放到教学楼里以后，前面还有几道很具体的关：导航栈能不能正常启动，车能不能稳定跟着路点走，闸机的窄通道怎么穿，玻璃门下面的 3cm 小台阶怎么过，还有一段没有地图特征的长走廊该怎么处理。

这一篇记录的就是从“有一张地图”到“车真的走完一条路线”之间的过程。

![室内交付小车的整体结构](/media/2026/08/indoor-cruise-vehicle.jpg)

## 1. 先把整套系统重新理清

这台车的底盘是前置双驱 DDSM115，后面是两个万向轮，电机由 ESP32 驱动板控制，串口一般是 `/dev/ttyACM0`。

传感器还是上篇的 Mid-360。需要再次强调一下：Mid-360 只有 LiDAR 和 IMU，没有轮速计，仓库里早期把它写成“带 odometer”是错误的。现在系统里的里程计是软件算出来的：

```text
/livox/lidar + /livox/imu
        ↓
icp_odometry
        ↓
robot_localization EKF
        ↓
/odometry/filtered
        ↓
Nav2 / base_driver
```

点云经过 `pointcloud_to_laserscan` 变成 `/scan`，给 AMCL 和 costmap 使用。`icp_odometry` 负责从点云中估计运动，IMU 给 EKF 提供姿态变化，AMCL 再负责 `map -> odom` 的定位。

底盘本身不提供一个可以直接相信的轮速里程计，所以不能简单理解成“轮子走了多少，车就走了多少”。这也是后面一些路段需要单独写反应式脚本的原因。

![小车正面的雷达、显示器和电控结构](/media/2026/08/indoor-cruise-chassis.jpg)

## 2. 每次上车前先做环境准备

我现在每次启动不会直接运行导航脚本，而是先加载 ROS 和自己的工作区：

```bash
source ~/dev_ws/setup.bash
```

这个脚本里固定了本项目使用的 `ROS_DOMAIN_ID=42`，也包含一些常用的构建和启动别名。

然后检查三件事。

第一，关闭 Cisco AnyConnect VPN。它的 nftables 规则有时会把雷达的 UDP 数据直接丢掉，表现就是点云和 IMU 都没有，终端却不一定立刻报一个很明显的错误。

第二，确认串口权限。插拔 USB 或者换接口以后，如果 `base_driver` 报 `/dev/ttyACM0` 无权限，可以先临时执行：

```bash
sudo chmod 666 /dev/ttyACM0
```

第三，确认主电池。主电池负责电机动力，USB 只给 ESP32 提供逻辑电源。电池亏电时串口仍然可能正常回帧，ESP32 的灯也会亮，但电机就是不转。这种时候继续改代码没有用，先查电池。

## 3. 先让导航栈完整启动

目前一楼大厅使用的地图是 `right_1st`。标准启动命令如下：

```bash
ros2 launch ~/dev_ws/launch/navigation.launch.py map:=right_1st \\
  init_x:=-0.3887 init_y:=-1.3948 init_yaw:=-1.5027
```

默认会同时启动传感器、ICP 里程计、EKF、AMCL、Nav2 和底盘驱动。启动之后不能马上发目标，要等定位和导航两个生命周期管理器都打印：

```text
Managed nodes are active
```

如果只等到了其中一条，另一个 `controller_server` 还没有 active，这时发目标经常会遇到“目标被拒绝”或者 `controller_server inactive`。我之前遇到过几次，看起来像是路点或地图错了，实际只是启动时机太早。

## 4. 路点巡航：先绕开容易抖的全局规划

路点放在 `config/waypoints.yaml` 里。常规的 Nav2 路点导航可以用 `waypoint_navigator.py`，但在当前大厅地图上，NavFn 在长直走廊里容易抖偏，所以实际巡航主要使用 `follow_line.py`。

这个脚本读取两个路点，生成一条密集的直线路径，直接送给 Nav2 的 `FollowPath` 控制器：

```bash
python3 ~/dev_ws/scripts/follow_line.py start_point turn1 rm_lab
```

实测 `start_point -> turn1 -> rm_lab` 约 32m 可以一次跑通。这样做的好处是路线意图很明确，车不需要在一条本来就应该直走的走廊里反复重新规划；AMCL 和 EKF 仍然负责告诉控制器“我现在偏到哪边了”。

一楼大厅的路线则是：

```text
elevator
  -> turn_point1
  -> gate_front
  -> gate_end
  -> glass_door
  -> turn_point2
  -> turn_point3
```

最初期的小车，只有一个框架

## 5. 第一关：宽 0.75m 的闸机

闸机通道大约 0.75m，车宽约 0.48m，看起来有余量，但对一台会产生横向漂移的差速车来说，余量并不算大。直接让 Nav2 贴着地图上的路径穿过去，实车容易蹭到柜体。

所以闸机这一段没有继续依赖全局规划，而是单独使用 `gate_cross.py`。它只读激光扫描，在通道里根据左右距离做居中控制，并用 EKF 的航向做小幅修正。

启动全程脚本：

```bash
~/dev_ws/scripts/cruise_right1f.sh
```

车到 `gate_front` 后先停下来，人工刷卡开闸。开门后，人要退到车的左侧或正后方，不能站在车的右前方。原因是透明闸机本身不容易被激光稳定看到，如果人站在右前方，人的身体会被当成右侧近墙，AMCL 的航向和闸机脚本的左右距离都会被污染。

这个问题的现象很有特点：车几乎只往左偏，很少自动往右修正，最后撞到中间柜体。后来把人员位置移开，并在进入闸机前保留一个约 5° 的航向补偿，才把这段稳定下来。

过闸后再用：

```bash
python3 ~/dev_ws/scripts/set_initial_pose.py --waypoint gate_end
```

重新给 AMCL 一个路点锚点，清掉过闸期间可能膨胀的定位协方差，再继续向玻璃门走。

## 6. 第二关：玻璃门下面的 3cm 台阶

玻璃门比闸机更麻烦。门框对激光的反馈不稳定，车直着对门洞时，前轮碰到下面的 3cm 小台阶，车体会被拧偏，随后 IMU 航向保护又可能把运动停掉。

解决方法不是把速度一味调高，而是让车以一个小角度斜着穿过门洞。现场使用的是朝西南方向约 20° 的姿态；早期尝试过更大的角度，结果斜着冲上台阶以后车体被拧得更厉害，反而不稳定。

这一段由 `cross_threshold.py` 负责，典型调用参数是：

```bash
python3 ~/dev_ws/scripts/cross_threshold.py --now --ros-args \\
  -p charge_speed:=0.45 -p recharge_speed:=0.5 -p pass_dist:=1.2 \\
  -p retreat_dist:=0.3 -p zone_cap:=2.0
```

它的思路是先以温和速度冲过门槛；如果前进过程没有顺利越过，就后退一小段，重新调整后再尝试。跨过门槛后，脚本再把车引到 `turn_point2`，最后对正 `turn_point3`，进入长走廊。

## 7. 第三关：没有地图可用的长走廊

玻璃门之后有一段约 28m 的长走廊。这里没有足够可靠的地图特征，继续让 Nav2 追地图容易把误差越积越大，所以我没有让车“相信地图”，而是写了 `corridor_glide.py` 做反应式直行。

它主要观察车体左右的激光距离，让车保持在走廊中间或沿右墙前进。走到出口后，右侧突然变成开阔区域，脚本把这个几何变化当作到达室外的信号，自动减速停车。

这段的启动方式是：

```bash
~/dev_ws/scripts/cruise_right1f.sh corridor
```

如果从头开始，则直接运行：

```bash
~/dev_ws/scripts/cruise_right1f.sh
```

脚本会依次完成电梯口到拐点、闸机、玻璃门台阶和长走廊。中间任一段失败都会停止，避免后面的脚本在错误位置继续发速度指令。

## 8. 跨楼层：用两张地图接上电梯

楼层切换不能只靠一张 2D 地图解决。当前做法是三楼使用 `3rd`，出电梯以后切换到一楼的 `right_1st`，再重新给 AMCL 设置一楼的初始位姿。

电梯脚本的核心不是猜“哪一部电梯会来”，而是保存关门时的激光基线，然后观察左右门扇区域的距离变化。实车测试时，关门距离大约 2.5m，门打开后对应区域会跳到约 4.0m，这个变化很明显。

三楼下到一楼的流程命令是：

```bash
~/dev_ws/scripts/elevator_3f_to_1f.sh
```

脚本会先从 `start_point` 转向电梯墙，后退到观察位置，检测哪一侧门打开，转向门洞并尝试进梯。人需要配合按呼梯键和楼层键，进入轿厢后脚本会暂停等待继续。

这里需要说明实际完成度：电梯开门检测已经实车验证，进梯状态机和出梯换图脚本已经准备好，但整段三楼到一楼的电梯流程还没有作为完整实车路线稳定复现。因此这部分目前是“检测已验证、整段待实跑”，不能写成已经交付。

## 9. 几个最后才确定的坑

### 车不动，但串口正常

先看主电池，不要先翻 `invert_left` 和 `invert_right`。当前运动学已经锁定：左电机 `left_id=2`，右电机 `right_id=1`，右侧方向做反向映射。电池动力不足时，ESP32 仍然能通信，最容易误判成软件问题。

### 点云和 IMU 全部没有

先关 VPN，再确认工作区和 `ROS_DOMAIN_ID`。如果只启动了某个终端，没有 source 正确的工作区，也可能出现节点看似启动但互相发现不到的情况。

### 雷达安装后运动方向像反了

现在的静态 TF 已经考虑了雷达安装姿态，`/scan` 也使用了对应的镜像处理。不要只看 RViz 里的箭头就直接改电机反向；先检查 `base_link -> livox_frame`，否则可能把传感器坐标问题改成底盘问题。

### Nav2 提示目标被拒绝

重新确认两个生命周期管理器都已经 active。多次反复启动后如果 DDS 握手异常，可以先干净退出旧进程，再重新启动整套导航栈。

## 10. 从“能跑”到“有人会用”：车载屏幕前端

导航脚本跑通以后，还不能直接交给别人使用。`screen_ui` 是车上的触摸屏前端，项目里把它叫作 Lumeo 车载配送界面。它负责的是任务交接，不是替代 ROS 导航栈。

打开配送流程后，屏幕先让操作员选择目的地，再展示卫星底图和已经实测过的路线。当前 E 教学楼路线约 1.0km，路线由 204 个 GPS 投影点组成。界面右上角会显示路线是否就绪，底部给出目的地、距离、预计时间和继续按钮。

![Lumeo 车载配送界面的目的地选择页](/media/2026/08/lumeo-screen-route-selection.png)

预告：室外巡航

这层界面和导航栈之间通过 ROS 话题连接：

```text
屏幕 -> /screen/route_cmd -> 导航栈
导航栈 -> /screen/progress -> 屏幕
```

发车时发送的是带有 `route_id` 和 `session_id` 的 JSON；运行过程中导航栈回传进度、当前路段、速度和预计剩余时间。二维码交接和顾客手机追踪则通过单独的 `cloud_bridge` 写入 CloudBase。

这里有一个很重要的边界：演示模式只展示路线和进度，不连接真实 ROS，也不会向 `/screen/route_cmd` 发布控制指令。真实模式连接失败时，界面应该保持离线并禁止发车，不能为了“看起来正常”自动切换成假进度。

## 11. 现在跑通了什么

截至目前，一楼大厅路线已经在真实教学楼里连续成功多次，包含：

```text
电梯口
  -> 闸机
  -> 玻璃门与小台阶
  -> 无图长走廊
  -> 室外走廊出口
```

三楼的实验室配送路线也已经跑通。跨楼层部分已经完成门洞检测和进出梯逻辑的开发与仿真验证，下一步是把人按键、门开窗口和换图重定位放到完整实车流程里反复测试。

上篇解决的是“雷达能不能看到、地图能不能建出来”，这一篇解决的是“地图之外的现实障碍怎么处理”。实际机器人项目最后往往不是某一个算法节点决定成败，而是定位、底盘、电源、人员位置、门槛和脚本退出行为一起决定的。
